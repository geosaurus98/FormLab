# Architecture

## Goals that shaped it

Reliability, offline use, privacy, low cost and maintainability by one developer. That leads to: **no backend**, a **local database as the source of truth**, **pure calculation functions** that are easy to test, and **thin UI** on top.

## Stack

React 18 · TypeScript (strict, `noUncheckedIndexedAccess`) · Vite 5 · Tailwind CSS 3 · React Router 6 · Dexie 4 (IndexedDB) · Zod · Recharts · vite-plugin-pwa (Workbox) · Vitest · Playwright.

The UI primitives in `src/components/ui` follow the shadcn/ui pattern (Tailwind plus small composable components), written in place instead of generated by the CLI, so the project has no Radix dependency tree.

## Layers

```
src/
  lib/            dates, units, ids, formatting: tiny and dependency-free
  domain/         PURE logic plus Zod schemas, grouped by domain; no IndexedDB, no React
    shared/       provenance (data-quality labels), preferences schema
    nutrition/    nutrients, foods, diary snapshots, targets & energy estimation
    recipes/      types, nutrition, scaling, versions, shopping, safety/substitutions, lab
    planner/      meal plans, explainable recommendations
    workouts/     types, session building/mutation, progression, records, timer, cardio, alternatives
    body/         weigh-ins, rolling averages, trends
    insights/     day aggregation, adherence, group comparisons, correlation
  data/           seed reference data (foods, ingredients, recipes, exercises, equipment, example programmes)
  db/             Dexie schema, seeding, services (transactions + validation), backup/restore, sync interface
  hooks/          live-query helpers (usePrefs, useToday, useNow, useNutritionLookup…)
  components/     design system, nutrition display helpers, charts, toast
  features/       one folder per section (home, food, recipes, planner, groceries, lab, workouts,
                  exercises, progress, insights, settings)
  app/            layout/navigation, PWA update prompt, local reminder loop
```

**Rule:** `domain/` never imports from `db/`, `features/` or React. Services in `db/` combine domain functions with persistence. Feature components read with `useLiveQuery` and write through services, or directly to Dexie for trivial single-field updates.

## Module boundaries

The three modules share entities but stay independently maintainable:

- FuelTracker depends on recipes only through `RecipeServingSnapshot`, a plain object with per-serving nutrients and the version id. Diary entries store their own snapshot, so the diary never needs the recipe again.
- WorkoutLab sessions embed their exercise blocks and a snapshot of targets, so editing templates or exercises never changes history.
- Insights only reads, using the aggregation functions in `domain/insights`.

## Key decisions

| Decision | Why |
| --- | --- |
| Immutable `RecipeVersion` plus diary snapshots | Logged history must not change silently when recipes or foods are edited |
| Records computed from history, not stored | Editing a completed workout can't leave stale personal records behind |
| Machine/cable comparisons keyed by gym (and variant) | Different leg-press machines aren't comparable |
| Rest timer stored as timestamps (`endsAt`) | Stays correct when the tab is throttled, backgrounded or reloaded |
| Active workout autosaved on every change | An interrupted session is fully recoverable |
| `null` = unknown nutrient, with missing counts tracked | Avoids false precision |
| Rule-based, explained recommendations | Transparent; no AI dependency or cost |
| Single active workout at a time | Avoids confusing parallel sessions |
| Validation status updated in place | It's metadata about a version (e.g. "I tested this"), not cookable content |

## Bundles

Home, the food diary and add-food flow, and the workout screens are in the main bundle, so the most frequent actions open instantly. All other screens load lazily via `React.lazy` with a `Suspense` fallback in `Layout`. Vendor code is split into `react`, `data` (Dexie, Zod) and `charts` (Recharts) chunks. The service worker precaches every chunk, so lazy loading doesn't affect offline use.

## Offline and PWA

`vite-plugin-pwa` precaches the whole built app (`generateSW`, `navigateFallback: index.html`). Every feature runs on IndexedDB, so nothing needs a network connection. Updates use a *prompt* strategy (`UpdatePrompt`), so a new version never reloads mid-workout. There are no network operations to queue, because there are no remote calls. Future integrations should use the adapter interfaces below and record results with an `ImportRecord`.

## Integration seams (interfaces only, no fake implementations)

- `FoodDataProvider` (`domain/nutrition/foods.ts`): external food databases or barcode lookup
- `ActivitySourceAdapter` (`domain/workouts/cardio.ts`): Android Health Connect, GPX and similar. Use `isLikelyDuplicate` to avoid double-counting.
- `SyncAdapter` (`db/sync.ts`): optional future multi-device sync. Records carry `id` and `updatedAt` for last-writer-wins; immutable records merge by id.

## Notifications and reminders

`app/reminders.ts` checks reminders every minute while the app is open and fires each one at most once per day. If notification permission is granted and the page is hidden, it shows a notification; otherwise it shows a toast. Rest-timer alerts use `setTimeout`, sound and vibration, plus an optional notification. Background delivery after the OS freezes the app isn't guaranteed without a push server, and the UI says so.
